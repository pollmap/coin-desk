## 운영 사용자 흐름

두 운영 주소의 390·1000·1280px에서 검색 → PENGU RSI → 데이터 정보 → 날짜 고정 → 저장 → 복원 → 새로고침을 모두 통과했습니다. 각 시장 첫 진입은 일괄 조회 1개이며 쓰기 API를 호출하지 않았습니다. Pages의 검증용 저장 설정을 파일로 내보내 VPS 주소에서 복원하고 동일 코인·날짜·값을 확인했습니다. 사용자 개인 자료 대신 격리된 브라우저 문맥의 검증용 설정을 사용했습니다.

모바일 차트 시작점은 266px·높이 330px, 1280px PC는 시작점 226px·높이 440px입니다. 운영 흐름의 axe 위반은 0개입니다. 실제 Windows Chrome에서도 ETH 검색·Enter 이동·실제 가격 갱신·MVRV 1.06배와 10월 8일 확정 기준일·데이터 정보 닫기를 확인했습니다. 이는 Apple Safari 검사가 아닙니다.

## 실제 데이터와 예약 수집

Coin Metrics 원천과 운영 API의 최신 MVRV 33개·TRX 활성 주소 1개를 대조해 값과 기준일이 모두 일치했습니다. 이는 34개 조합의 직접 대조이며 모든 온체인 지표의 독립 원천 대조는 아닙니다. [대조 기록](source-comparison.json)

배포 직전부터 319초의 읽기 전용 비교에서 네 수집 lane이 각각 5회 정상 완료했습니다. 기존 시세 210개의 확인 시각과 200개의 가격 기준 시각이 증가했고, 선물 128개 원천의 성공 확인 시각이 증가했습니다. 과거 선물 50개 파티션에서 각각 200개씩 총 10,000개, 최근 관측 306개가 늘었습니다. 일일 과거 후보 예약 한도 10,000개는 그대로입니다. 검사 중 직접 수집 API·overview는 호출하지 않았으며 검사 SQL 쓰기는 0입니다. 다른 방문자의 부재는 보장하지 않습니다. [자연 갱신 기록](natural-cron.json)

위 관측 구간이 끝난 뒤, 배포 이전의 일반 시세 검증 오류가 남긴 긴 재시도 대기 23건과 컨테이너 교체 종료 직전에 남은 1건의 재확인을 한 번 앞당겼습니다. 변경한 열은 `ingestion.next_attempt`이며 기존 오류·실패 횟수·마지막 성공·가격은 보존했습니다. HTTP 장애는 대상에서 제외했고 실제 검증과 저장은 다음 예약 수집이 수행했습니다. 이를 쓰기 없는 자연 관측 구간에 합산하지 않습니다.

## 성능과 남은 제한

후보의 실제 스트림 100개 연결·10개 재연결은 모두 성공했습니다. 같은 VPS에서 측정한 수신 지연 p95는 940ms, 후보 API 메모리는 68.55~79.80MiB였습니다. 브라우저 화면 반영 시간과 다른 측정입니다. 최종 운영·성능 수치는 별도 JSON에 기록합니다.

저유동성 종목의 체결 지연, 짧은 신규 상장 이력, 진행 중인 과거 선물 수집을 완료나 정상으로 바꾸지 않습니다. 150개 모두의 MVRV를 지원하는 것도 아닙니다. 실제 Safari·VoiceOver와 사람 대상 사용성 검사는 미검증이며, 48시간 대기는 완료 조건에 넣지 않습니다.

모바일 정보창 버튼을 처음 추가했을 때 행 높이가 79.9px로 늘어나는 회귀를 Chromium/WebKit에서 발견했습니다. 상태 버튼은 24px 높이를 유지하고 해당 행의 위아래 간격을 줄여 76px 이하와 초점 복귀·axe를 다시 통과했습니다. 최초 실패를 최종 통과로 합산하지 않습니다.

최근값만 시드로 넣은 선물 파티션에는 과거 커서가 생기지 않던 코드 경로를 수정했습니다. 최근 확보를 전체 과거 확보로 표현하지 않습니다. 기존 원문과 완료 기록이 있는 이력은 재시작하지 않고, 하루 10,000개 과거 후보 제한을 유지합니다.

가격 지연은 원천 거래 부재와 HTTP/검증 실패로 나눕니다. 원천 실제 거래 시각은 바꾸지 않습니다. [업비트 필드 정의](https://docs.upbit.com/kr/reference/list-tickers)에 따라 전일 UTC 대비 등락을 24시간 수익률로 사용하지 않습니다.

성능 비교는 주소별 새 브라우저 문맥 5회, Chromium 153, 1280×800, 다운로드 10Mbps·업로드 5Mbps·추가 지연 0·CPU 1배 조건입니다. 배포 전 일부 표본이 로컬 빌드·검사와 겹쳤으므로 개선 효과의 단독 근거로 사용하지 않습니다. LCP와 실제 가격 준비 시각은 서로 다른 측정입니다. [LCP 측정 구분](https://web.dev/articles/optimize-lcp)

사용자가 작성 중인 별도 기획서와 개인 원본은 이번 변경·커밋에 포함하지 않습니다. 자동 브라우저 검사는 실제 Apple Safari/VoiceOver 또는 사람 대상 사용성 검사를 대체하지 않습니다.

첫 원격 CI `37987068474`는 185개 통과·5개 실패·2개 개인 경로 제외였습니다. 실패는 검색 직후 Enter 1개와 WebKit 768~1440px 시세 버튼의 최소 클릭 영역 4개입니다. 버튼을 전 폭에서 24px로 맞췄습니다. 첫 검색 수정 뒤 반복 검사에서도 12개 중 2개가 실패해, URL 갱신에 따른 입력 초기화를 제거하고 Enter 시 입력값을 직접 읽도록 추가 수정했습니다. 최종 결과는 별도 기록합니다.

최종 코드의 앞선 Windows 병렬 반복 검사에는 정보창 버튼 클릭 시간 초과 1회가 남았습니다. 원인은 확정하지 않았습니다. 같은 코드의 직렬 12회 반복과 원격 전체 회귀는 재시도 없이 통과했으며 앞선 실패를 없던 것으로 처리하지 않습니다.

원격 CI `37989976218`에서는 브라우저 190개까지 통과한 뒤 Docker Hub 이미지 조회가 HTTP 429로 실패했습니다. [공식 Docker 이미지 미러](https://aws.amazon.com/blogs/containers/docker-official-images-now-available-on-amazon-elastic-container-registry-public/)와 기존 원천의 매니페스트 해시가 동일함을 확인해 CI에서 같은 해시를 고정했습니다. 계산·브라우저·컨테이너 검사를 별도 job으로 나누고 모든 결과가 성공해야 `verify`가 통과하도록 했습니다. 검사 수·재시도 기준·운영 런타임 버전은 완화하지 않았습니다.

운영 검증 도구의 첫 실행에는 Windows 기본 인코딩으로 UTF-8 명부를 읽은 오류와 Pages의 SPA 경로 `/healthz`를 JSON으로 읽은 오류가 있었습니다. 명시적 UTF-8과 실제 VPS `/healthz` 경로로 수정했습니다. 제품 API 장애로 집계하지 않습니다.

[Binance 공식 정의](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md#24hr-ticker-price-change-statistics)의 `closeTime`은 통계 종료 시각입니다. 새 시세 정보창은 이를 마지막 체결로 부르지 않습니다. 샘플 조회에서도 동일 거래 ID의 PENGU `closeTime`과 체결 시각 사이에 607ms 차이가 있었고, 이 차이를 0으로 보정하지 않았습니다. 스냅샷의 시각과 실제 스트림 체결 시각은 별개입니다.


## 최종 운영 성능

주소별 새 브라우저 문맥 5회 표본입니다. 5회에서 p95는 최댓값이며 장기 서비스 수준 보장이 아닙니다.

| 주소 | 배포 전 LCP p95 | 배포 후 LCP p95 | 스트림 수신→화면 p95 상한 |
|---|---:|---:|---:|
| pages | 4876ms | 3176ms | 1574ms |
| vps | 2684ms | 3096ms | 1653ms |

운영 SSE 100개 연결·10개 재연결 모두 성공, 오류 0, 같은 VPS의 수신 지연 p95 1004ms입니다. 이 부하 검사에는 2개 읽기 API 검증 작업자가 함께 실행됐습니다. LCP 비교는 전체 읽기 검사가 끝난 뒤 별도로 실행했습니다. [성능](performance.json) · [SSE](sse-load.json)

150개 자산, 1472개 읽기 요청 중 PENGU 일봉 1개에서 30초 읽기 시간 초과가 발생했습니다. 동일 요청을 VPS에서 두 번, Pages에서 한 번 재확인해 366개 확정 일봉을 확인했습니다. 최종 미해결 연결 오류는 0이며 최초 시간 초과의 원인은 미확정으로 보존했습니다. 최신 데이터 상태는 정상 1539/1585이며 모든 원천이 정상이라는 뜻은 아닙니다. [연결 검사](data-connections.json) · [상태](status.json) · [최종 구분](final-status.json)

두 주소 모두 LCP p95 2.5초 목표를 넘었습니다. Pages 표본은 이전보다 줄었으나 VPS 표본은 늘었으므로 전체 성능 개선으로 단정하지 않습니다. 중앙 스트림 수신부터 화면 표시까지의 p95 상한은 두 주소 모두 3초 이내입니다.
