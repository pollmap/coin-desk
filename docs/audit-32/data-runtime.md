## 1. Binance의 실제 체결 시각

### 확인한 결함과 수정 계약

Binance `ticker.24hr.closeTime`은 24시간 통계창의 마지막 시각이며, 마지막 체결 시각을 증명하지 않습니다. 이전 저장 시세에 이 값을 실제 체결 시각처럼 사용하는 경로가 있었습니다. 기존 데이터를 최신 체결로 소급 판정하지 않고 읽기 단계에서 구분합니다.

| 필드 | 새 계약 |
|---|---|
| `time` | 실제 체결 `T`를 내림한 Unix 초. 기존 숫자 형식 유지 |
| `actualTradeAt` | 확인된 실제 체결 Unix 초. `time`과 일치해야 함 |
| `timestampKind` | 확인된 체결은 `trade`, 확인되지 않은 이전 Binance 통계값은 `ticker-window` |
| `sourceEventTime` | 원천 통계창·메시지의 시각. 체결 신선도 대신 사용하지 않음 |
| `lastTradeId` | Binance 원시 체결의 마지막 ID. 같은 시각의 순서를 구분하는 근거 |

Binance REST·WebSocket API의 ticker `lastPrice`·`lastId`를 aggregate trade의 가격 `p`·마지막 원시 체결 ID `l`과 대조합니다. 두 값이 모두 맞고 실제 체결 `T`가 ticker 통계창 종료 시각 이하일 때만 시각을 확정합니다. 값이나 ID가 다른 자료에서 시각만 가져오지 않습니다.

확인되지 않은 이전 스냅샷은 `actualTradeAt=null`로 읽으며 마지막 가격 자체는 보존합니다. 새로운 체결을 확인하기 전까지 통계창의 시각을 최근 체결로 표시하지 않습니다. 실제 체결 기준 **300초**, 미래 시각 허용 **60초**는 유지합니다. 요청 장애와 특정 코인의 오래된 체결·시각 미확인은 별개입니다. 요청 장애에 대한 거래소 전체 재시도와 개별 실패 코인의 스냅샷·오류·재시도 보존 정책도 유지합니다.

화면에서 초로 내림한 저장 시세와 소수 초가 있는 스트림을 합칠 때, 같은 초의 오래된 tick이 최신 저장값을 덮을 수 있는 회귀도 확인했습니다. Binance의 두 값이 같은 초면 원시 체결 ID를 함께 비교합니다. 저장 ID 11에 대해 스트림 ID 10은 차단하고 12는 허용하며, 저장에 ID가 있는데 스트림 ID가 없으면 최신이라는 증거로 채택하지 않습니다. 마지막 수정에는 이 세 조건의 회귀 검사를 추가했습니다. 최종 통합 실행 결과는 별도 기록으로 확인합니다.

근거: [Binance 공개 시장 데이터 정의](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/ws-api/market), [Binance WebSocket API](https://developers.binance.com/en/docs/products/spot/web-socket-api).

### 중앙 시세와 제한된 보조 확인

- 중앙 `quote-hub`는 자산별 최근 64개 aggregate trade 증거를 메모리에 보관합니다. 모든 틱을 DB에 저장하지 않습니다.
- 내부 `/snapshot`은 선택한 허용 자산만 최대 8개 반환합니다. 공개 SSE 연결 수를 소비하지 않으며, 외부 임의 URL을 요청하는 기능이 아닙니다.
- 수집기의 내부 reader는 Compose의 `quote-hub` 또는 loopback 주소만 허용합니다. 사용자명·비밀번호·추가 경로·쿼리·fragment가 있는 주소는 거부합니다.
- 중앙 증거 대기는 최대 600ms입니다. 일치하는 자료가 없으면 공개 `trades.aggregate` 요청을 자산당 최대 한 번, 동시 2개로 확인합니다. 확인 배치의 전체 deadline은 4초, 개별 요청은 남은 시간 안에서 최대 1.5초입니다. 끝까지 증명하지 못한 자산은 시각 미확인으로 남습니다.
- 기존 150개 종목 수집은 거래소별 기존 배치 구조를 유지합니다. 콜드 스타트의 보조 요청은 최악의 경우 자산당 한 번까지 발생할 수 있으므로 모든 자산이 한 번의 예약 실행에서 시각을 확정한다고 주장하지 않습니다.

공식 aggregate 요청 weight는 4입니다. 150개가 모두 보조 요청을 필요로 하면 해당 요청 자체의 최대 합계는 600이며 ticker·연결 등의 별도 weight가 추가됩니다. 제한 응답은 원천의 `retryAfter`에 따라 대기합니다. 시각 증명 deadline을 넘은 요청을 무한히 기다리지 않습니다.

검사 중 공개 WebSocket API 연결을 요청마다 새로 만드는 보조 경로가 발견됐습니다. Binance는 IP별 **5분간 연결 300개**, 연결당 weight 2를 명시합니다. Node 수집 프로세스는 이제 공개 API 연결 하나를 재사용하고 응답 ID로 요청을 구분합니다. pending 최대 32개, 개별 timeout, 5초 idle 종료, 연결 실패 시 정리·재연결, 429/418 대기를 검사했습니다. 인증·거래 요청은 지원하지 않습니다.

## 2. 상태 진단과 기존 데이터 보존

| 상황 | 상태·진단 |
|---|---|
| 실제 시각을 증명한 체결이 300초 초과 | `TRADE_STALE` · 최근 거래가 오래됨 |
| 이전 Binance 통계창 시각만 있거나 증거가 불일치 | `TRADE_TIME_UNKNOWN` · 실제 체결 시각 미확인 |
| 명시적인 통계창 시각 오류 | `QUOTE_WINDOW_STALE` · 시세 통계 기준 시각 지연 |
| Bybit 등의 지표 관측이 오래됨 | 기존 `OBSERVATION_LATE` · 관측 지연 |
| 거래소 요청 자체 실패 | 기존 요청 오류·거래소 전체 재시도 |

이전 health 경로는 Binance의 오래된 실제 체결을 통계창 지연으로 바꾸는 분기가 있었습니다. 새 경로는 snapshot의 작은 시각 메타데이터만 함께 읽어 실제 체결과 미확인을 구별합니다. 잘못된 JSON을 읽을 때도 쿼리가 전체 실패하지 않도록 보호합니다. 전체 snapshot 본문을 상태 응답에 추가하지 않습니다.

시세의 수집 성공 시각이 새로워도 실제 체결이 오래됐으면 정상으로 바꾸지 않습니다. 스트림 연결 정상, 프로세스 health 정상, 모든 원천의 신선도 정상은 서로 다른 판단입니다. 배포 전 읽기 전용 운영 DB 표본에서 BTC·DOGE·ETH Binance 스냅샷의 새 시각 메타데이터가 모두 없음을 확인했으므로, 운영 수집기 교체 전까지 이 계약이 실제 저장에 적용됐다고 표현하지 않습니다.

기존 관측 링크도 exact ID로 조회할 수 있도록 보완했습니다. `signals?asset=…&id=…`는 최대 400자의 제한된 ID를 검증하고 해당 자산·ID만 읽습니다. 수정·철회된 관측도 조회해 상태를 보여주며, 다른 코인의 ID나 없는 ID는 빈 결과입니다. 읽기 때문에 관측 상태나 개인 자료를 변경하지 않습니다.

## 5. VPS 공간과 개선 가능 범위

2026-10-13 10:00:55 UTC 읽기 전용 조사에서 서비스 볼륨의 여유 공간은 **4,816,830,464바이트 = 4.486GiB**였습니다. 과거 이력 보호 기준 **8GiB**까지 **3,773,104,128바이트 = 3.514GiB**가 부족합니다. 뒤의 조사에서는 운영 쓰기 때문에 사용 가능한 공간이 4,756,480,000바이트로 줄었으므로 이 값은 고정 용량이 아닙니다.

| 보리차트 소유 범위 | 측정된 디스크 할당량 |
|---|---:|
| 운영 DB | 175,456,256바이트 |
| DB WAL | 4,284,832바이트 |
| DB 빈 페이지 | 1개 × 4,096바이트 |
| audit | 3,659,706,368바이트 |
| backups | 1,188,122,624바이트 |
| releases | 349,650,944바이트 |
| shared | 208,211,968바이트 |

압축 가격 이력 3,704행의 payload는 56,134,653바이트, 월별 네트워크 이력 3,787행의 payload는 43,495,913바이트였습니다. DB 빈 페이지가 4KiB뿐이므로 단순 DB 압축·VACUUM으로 3.514GiB가 생긴다고 주장할 근거가 없습니다. Docker의 전체 reclaimable 용량 조회는 15초 timeout이어서 미확인으로 남겼습니다.

삭제 없이 가능한 개선을 제한된 표본으로 측정했습니다.

- SHA-256이 완전히 같은 이전 백업 4개는 파일마다 38,350,848바이트이며 서로 다른 inode에 있습니다. 같은 내용 3개를 안전하게 중복 제거할 경우의 이론적 절감량은 115,052,544바이트입니다. 실제 중복 제거는 하지 않았습니다.
- 최신 백업 한 개와 감사용 복원 DB 한 개를 gzip level 3으로 스트리밍 측정해 각각 120,574,948·120,602,709바이트의 절감 가능성을 확인했습니다. 압축 결과는 저장하지 않았으며 원본·백업 복원 계약은 유지했습니다.
- 위에서 직접 확인한 절감량은 8GiB 부족분을 해결하기에 부족합니다. 다른 날짜·파일도 같은 비율로 압축된다고 가정하지 않습니다. 실제 변환은 내용 해시·독립 복원·기존 접근 경로를 검증해야 합니다.

추가 미사용 디스크도 확인했습니다. 부모 디스크는 150GiB, root·EFI·boot 등의 파티션 합계와 차이는 약 **2MiB**뿐입니다. 별도로 미마운트된 대용량 볼륨이 없고 ext4 예약 블록도 0입니다. 파티션 확대나 예약 블록 해제로 부족한 3.514GiB를 얻을 수 있다는 근거가 없습니다. format·mount·파티션·예약 블록 변경은 하지 않았습니다.

따라서 이 조사로 과거 이력 작업을 재개하지 않습니다. 최신 수집을 유지하면서 보존 가능한 압축·중복 정리의 실제 절감량을 검증하거나 추가 용량을 확보해야 합니다. 다른 프로젝트·운영 데이터·복구 자산을 삭제해 공간을 만드는 조치는 하지 않았습니다.

## 6. 배포 준비와 보존할 서비스

자원 조사 당시 current는 `vps-63b8b1d4ea587ca8`이고 이전 웹 릴리스는 `vps-52cb626ebda4bb20`입니다. API·background·recent·quotes·analysis·quote-hub·backup 컨테이너의 process health는 정상이며 read-only rootfs를 유지하고 있었습니다. 이는 각 원천의 데이터 신선도 정상과는 별개입니다.

이번 시세 계약을 적용하려면 새 hub의 proof endpoint와 quotes 수집기, 공통 공개 세션·진단을 사용하는 API를 함께 확인해야 합니다. background도 공통 provider를 사용하므로 변경된 코드를 적용할 서비스로 검토합니다. recent·analysis·backup과 기존 DB·볼륨·Nginx·다른 프로젝트는 필요한 변경 근거가 없는 한 보존합니다. DB 마이그레이션은 이번 계약에 필요하지 않습니다.

기존 `work/price-031-reading/remote_deploy.py`는 **API만 교체**하는 검증 도구입니다. compose·server runtime이 같고 API 외 서비스 설정이 완전히 동일하다는 조건을 강제하므로, 이번 여러 서비스 교체에 그대로 사용할 수 없습니다. 당시 API만 교체하기 위한 측정 자원 예외도 전체 서비스 배포의 허가나 8GiB 과거 수집 보호 기준 통과로 확대하지 않습니다.

안전한 실행 순서는 다음과 같습니다. **이 문서 작성 시점에는 준비 검토이며 원격 실행하지 않았습니다.**

1. PR·main CI의 Linux 이미지와 소스 산출물 SHA-256, OCI config·layer·amd64를 검증합니다. VPS에서 이미지 빌드는 하지 않습니다.
2. 새 이미지·압축 파일·독립 복원 DB·후보 컨테이너·롤백 이미지가 동시에 있는 동안의 추가 용량을 다시 계산합니다. 현재 여유 공간과 메모리로 검증한 범위만 준비합니다.

4. 온라인 SQLite 백업과 별도 복원본의 무결성·행 수·스키마·내용 해시를 검사합니다. 후보 API는 읽기 전용 복원 DB, 후보 hub는 격리된 내부 네트워크로 확인합니다.
5. hub의 실제 스트림 연결·선택 proof를 먼저 확인합니다. 처음에는 캐시가 비어 있을 수 있으므로 제한된 보조 요청과 시각 미확인 상태를 확인한 뒤 quotes·background·API를 단계적으로 교체합니다.
6. 서비스별 시작·health·적용 image ID와 보존한 컨테이너 ID를 비교하고, 실패한 단계만 이전 image/config로 되돌립니다. 코드 롤백과 DB 복원은 구분합니다.
7. 웹 자산을 반영하고 이전 정적 자산을 보존합니다. Pages·VPS 실화면에서 가격·지표 단위·상태·저장 복원을 확인합니다. 공개 주소가 달라져도 개인 IndexedDB를 서버로 옮기지 않습니다.
