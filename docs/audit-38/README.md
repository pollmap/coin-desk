## 배포 준비와 공간 확보 경과

공유 서버의 읽기 API 1개가 이미 삭제된 파일을 계속 열고 있던 상태를 해소해, 전후 여유 공간이 9,107,103,744 → 12,945,424,384바이트로 증가했다. 관측 증가량은 3,838,320,640바이트(약 3.57GiB)이며 동시 쓰기의 영향을 포함한다.

종료 절차는 SIGTERM 후 70초 동안 종료되지 않아 SIGINT를 한 번 보낸 뒤 같은 컨테이너를 다시 시작한 것이다. SIGKILL·이미지 교체·DB 쓰기·파일 삭제는 없었다. 종료 코드는 130이며, 열린 삭제 파일 34개가 재시작 후 0개가 됐다. 기존 구성·마운트·이미지·배포 파일과 메타데이터를 보존했고 독립 수집기는 유지했다. 해당 API에는 짧은 중단이 있었을 수 있으며 무중단으로 표현하지 않는다. 재시작 전후 health는 같은 응답으로 HTTP 200이었지만, 연결을 오래 유지한 근본 코드 원인은 이번에 수정하지 않았다.

10:44:51 UTC의 준비 전 재점검은 여유 공간 12.0558GiB, 사용 가능한 메모리 약 3.82GiB, 4 CPU에서 1분 부하 2.246이었다. 이후 준비와 격리 검사에 필요한 복사본을 만들고, 별도 승인된 닫힌 감사 SQLite 4개의 보존 압축을 수행했다. 각 원본을 유지한 채 gzip과 독립 디스크 복원본을 만들고, 전체 SHA256·스키마·모든 테이블 행 수·무결성과 uid/gid/mode/mtime/확장 속성의 일치를 검증한 뒤 비압축 원본 경로만 압축본으로 대체했다. 원본 바이트와 복원 명세는 모두 보존했으며 운영 DB·현재와 이전 릴리스·실패 배포 증거는 변경하지 않았다. 과거 수동 감사 스크립트는 정확한 원래 경로로 복원한 뒤 다시 실행해야 한다.

독립 디스크 복원 4건과 메타데이터 검증을 통과했다. 파일 할당량 차이는 521,224,192바이트(497.08MiB), 서버 여유의 전후 차이는 520,974,336바이트(496.84MiB)다. 두 수치는 동시 쓰기와 증거 파일 등의 영향을 받으므로 구분한다. 이 작업의 전후 여유는 10,085,134,336 → 10,606,108,672바이트였다. 도구 준비 당시 로컬 검사 5개 통과와 원격 미실행 상태도 이전 단계 기록으로 남겼다.

첫 격리 원천 검사는 CPU 부하 보호 때문에 완료 판정 전에 중단했다. 프로세스 종료 코드는 기록되지 않았고, 격리 컨테이너·브리지 정리는 완료했다. 시험 DB에는 `partial` 보고서 4개가 생성돼 읽기 전용으로 보존했지만, 이 문서의 존재는 첫 검사나 배포 통과 근거가 아니다. 두 번째 검사는 CPU 부하 3.2/4 CPU·사용 가능 메모리 1GiB·디스크 보호 8GiB·시간 제한·완료 판정을 유지한 채 별도 경로에서 통과했다. 첫 실행의 DB·로그·보고서는 덮어쓰지 않았다.

두 번째 검사의 전체 구간은 11:03:51~11:05:10 UTC의 79초, worker 관측 실행시간은 12.02초다. 관측 826개, 시장 메타데이터 417개, 선택 시장 5개(현물 2·파생 3), 보고서 4개를 검증했다. 원천·작업 오류와 필수 원천 누락은 없고 기존 21개 테이블·복원 원본은 그대로다. 기존 핵심 시세와 수집기의 자연 갱신 및 격리 컨테이너·브리지 정리도 확인했다. 보고서는 모두 `partial`이며, 기간을 완전히 확인하지 못한 값은 제외했다. 모든 시장·전체 기간의 완전성이나 원천 수치의 독립 재조회까지 통과했다는 뜻은 아니다.

11:04:42 UTC 읽기 점검에서 준비와 백업 검증은 유효했다. 백업 완료 시각은 10:49:39 UTC이며 기존 3,600초 기준의 만료 시각은 11:49:39 UTC다. 첫 활성화 직전에 나이·바이트 해시·독립 복원·기존 서비스 정체성을 다시 확인했다. 이후 첫 활성화는 백업 시작 대기시간으로 실패했으며 아래에 원인과 복귀 결과를 기록했다. 이 준비 백업의 당시 유효 판정은 새 재개에 적용하지 않는다. Pages 게시와 양 주소의 실제 차트·사전·보고서 검사는 아직 수행하지 않았다. 만료된 일회 선물 복구는 재시작하지 않는다. 이후 문서만 바뀌었다고 재배포하지 않는다.

## 로컬 구현 검증

- 타입검사 최초 실행은 통과했다. 이후 전체 검사를 병행한 환경에서 메모리 부족이 발생했고, 512MiB로 제한한 재검사 역시 메모리 부족으로 종료됐다. 최종 소스를 1,024MiB 제한으로 다시 검사해 통과했다. 빌드와 전체 회귀는 별도 원격 CI로 판정한다.
- 전체 단위 검사: 89개 파일, 950개 중 947개 통과·3개 실패. 실패는 기존 일반 축 기본값과 새 링크의 축 값 차이였다. 기본 진입 링크는 축을 강제하지 않고 공통 정책을 사용하도록 정리했다. 관련 단위 검사 22개가 후속 실행에서 모두 통과했다. 최초 실패를 삭제하거나 전체 단일 실행 통과로 합산하지 않는다.
- 축 브라우저 검사: Chromium·WebKit에서 고유 18개 검사를 두 실행으로 확인했다. 작은 가격·평탄 가격·넓은 가격 범위, 실제 음수 보조선의 일반 축 전환, 저장·날짜·확대 보존을 포함한다.
- Original 브라우저 검사: 최초 4개 통과·2개 실패에서 오류 상태의 준비 안내 중복을 발견했다. 이를 수정하고 정상·실패 상태의 부정확한 안내 부재까지 포함한 6개가 양 엔진에서 재시도 없이 통과했다.
- 설명·사전: 76항목을 양 엔진에서 순회했다. 통합 52개 중 50개 통과·2개 실패 후, 같은 실패 사례와 문맥 보존·도식 검사를 포함한 8개가 통과했다. 실패는 지연 로딩 모의가 새 모듈 요청을 다시 가로막은 문제와 WebKit 프로세스 종료였다.
- VPS 관련 Python 133개, Node metadata 4개, 설명 관련 단위 94개가 통과했다. 실제 운영 백업·복원은 아직 별도 단계다.
- 독립 코드 검토에서 Original 모델 ID가 자체 회귀 전환에 남는 결함을 발견했다. 서로 다른 모델로 전환할 때 모델 설정을 제거하고, 같은 모델을 다시 열 때는 보존하도록 수정했다. 양방향 전환과 저장 URL의 모델·축 복원 단위 검사를 통과했다.

새 백업 작업은 전용 프로세스 묶음에서 CPU 25%·메모리 512MiB·swap 0, 최대 1,800초와 종료 여유 60초로 제한한다. 바깥 대기는 1,920초, SSH는 1,950초다. 서비스 활성화의 4,200초와 백업 시작·복귀 900초는 유지하며, 시간 초과는 실패로 보존하고 자동 재시도하지 않는다. v2의 오프라인 16개(0.677초)와 독립 최종 검토가 통과했다. 이는 실제 서버에서 새 백업·복원·재개가 통과했다는 뜻이 아니다.

## 닫힌 감사 자료의 보존 이관

11:59:27~11:59:40 UTC에 과거 감사 자료 2묶음·6파일의 보존 이관을 완료했다. 원본 371,343,360바이트를 압축본 118,132,980바이트와 독립 원본 복원본으로 각각 영구 보관했다. 복원본의 실제 할당량은 NTFS 압축 적용 후 176,803,840바이트다. 전체 SHA256·SQLite 스키마·모든 테이블 행 수·무결성을 대조하고 원래 소유자·권한·시각·확장 속성과 복원 명세를 보존한 뒤, 서버의 해당 원본 경로만 제거했다. 원본 데이터 바이트를 버린 작업이 아니다. 운영 DB·정기 백업·실패 중간 백업은 대상에서 제외했다.

제거한 원본 파일 할당량은 371,351,552바이트다. 직전·직후 서버 전체 여유의 동일 조건 측정이 없어 이를 순수 공간 증가량이라고 주장하지 않는다. 두 번째 완료 시점의 서버 여유는 7,843,528,704바이트이며 이후 동시 쓰기로 달라졌다.

세 번째 묶음의 이전 전송은 CPU 보호로 중단돼 부분 압축본과 실패 기록을 남겼다. 명시적인 세 번째 시도의 로컬 전송·독립 복원 검사는 통과했다. DB 본체 364,888,064바이트와 sidecar 32,768바이트, 합계 364,920,832바이트를 보존했으며 압축본은 93,639,107바이트, 독립 원본 복원본의 할당량은 140,234,752바이트다. 12:11:43 UTC까지 원격 원본 정체성·참조 확인은 통과했지만 CPU 부하 때문에 보존 전환을 실행하지 않아 서버 원본 경로는 남아 있다. 네 번째 묶음의 완료도 주장하지 않는다.

12:11:43 UTC의 마지막 정상 확인값은 여유 7.375GiB·부하 3.567/상한 3.2로, 당시에도 새 백업과 재개를 시작할 조건에 미달했다. 이후 12:15 UTC경 SSH·VPS HTTPS 연결 거부와 Pages 시세 요청 실패를 관측했다. 정적 Pages 화면은 열렸으나 원인은 미확정이며, 현재 서버 자원·서비스 건강 상태를 다시 확인하지 못했다. 새 v2 백업·활성화·Pages 게시·후속 운영 검증은 수행하지 않았다.

Pages에 대한 Python 요청의 HTTP 403은 단독 장애 근거로 사용하지 않았다. 실제 브라우저에서 정적 화면 로딩과 “시세를 가져오지 못했습니다.” 표시를 별도로 확인했다. 이 접속 실패 구간에 새 배포·서비스 변경·세 번째 원본 보존 전환·새 백업 실행은 없었으며, 복구와 원인은 아직 확인되지 않았다.
